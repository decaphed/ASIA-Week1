# Training CSV Upload & Model Reset — Design Spec

**Date:** 2026-08-23
**Status:** Approved design, pending implementation

## Problem

The only Tier 2 model today is the one-off bootstrap fit from a git-committed `data/train.csv`, trained and promoted entirely via manual CLI (`python -m pdm.app.training fit ...` piped into `recordBootstrapRun.js`). There is no way for anyone to retrain from new data without shelling into the container, no quality gate on what gets trained, and no way to compare a new candidate against the currently-deployed model before it goes live. Separately, the "Needs Review" tab in `PredictionsPage.jsx` renders its entire queue with no cap, forcing endless scrolling on a busy queue.

## Scope

**In scope:**
1. Wipe the current live Tier 2 artifact so the app starts over with Tier 1 only.
2. A CSV upload surface, open to anyone (no auth/group gate — deliberate, "for now"), that quality-checks and preprocesses an uploaded training CSV, rejecting it with reasons if it fails.
3. A fit → compare → deploy loop: a passing CSV can be fit into a **candidate** model, whose metrics are shown next to the currently-deployed model's metrics, and only deployed if the operator explicitly chooses to.
4. A "Show more / Show less" cap on the Needs Review queue list.

**Out of scope:** retraining from the existing `training_corpus`/`retrain.py` champion-challenger loop (unchanged, orthogonal to this bootstrap-style path per `training.py`'s own module docstring), authentication/authorization on the new endpoints, deleting or hiding any existing Tier 2 FE code (badges, source pills, drawer fields) — it stays as-is and simply has nothing to render once the artifact is gone, multi-class labels (still binary NORMAL/FAULT), any change to the live sensor-window quality pipeline (`preprocessing/quality.py`) which is a different concern (per-window sensor data, not tabular training CSVs).

## Design

### 1. Start over (artifact reset)

A new `POST /training/reset` endpoint in `pdm/app/main.py` deletes `PDM_ARTIFACT_DIR/model.joblib` and `metadata.json` if present, and reassigns `model.py`'s module-level `_artifact` to `None` in place (no container restart). After this, `model.score()` always returns `None`, so `/score`'s Tier 2 augmentation never fires — the existing FE badge/source-pill code (`faultEvents.js`, `PredictionsPage.jsx`, `ReviewDrawer.jsx`) is untouched but naturally shows nothing Tier-2-sourced, satisfying "detach from front end" without deleting any of that code. Wired to a "Reset model" button in the new Train Model panel (with a confirm dialog — this is destructive).

### 2. Training CSV quality gate + preprocessing

New module `pdm/app/training_quality.py`, mirroring `preprocessing/quality.py`'s "weighted score, hardcoded reasons" shape but for a tabular training CSV rather than a sensor window:

- **Structural checks (hard fail, no score computed):** required columns present (`training.TRAIN_CSV_COLUMN_MAP` keys + `TRAIN_CSV_LABEL_COLUMN`), at least `MIN_ROWS` rows (config constant, default 200 — a stratified split needs enough of each class to be meaningful).
- **Scored checks (weighted, same shape as `compute_quality`):**
  - missing-value rate across required columns (rows with any NaN in a required column)
  - duplicate-row rate (exact duplicate rows)
  - out-of-range rate — reuses `physics.load_ranges()` bounds (same RANGES `preprocessing/validator.py` already validates live samples against) to flag values outside the metric's physical range
  - label balance — the minority class's share of rows must clear `MIN_MINORITY_SHARE` (default 0.05); below that, `stratify=y` in `training.fit_model`'s split is unreliable and metrics would be meaningless
- **Score/verdict:** same 0-100 weighted formula pattern as `compute_quality`, `PASS` at `>= 70`, else `REJECTED`, returned with per-check reasons (which columns had missing rates, which rows were out of range, the label counts) so the FE can show *why* a CSV was rejected, not just that it was.
- **Preprocessing on PASS:** drop rows with missing required-column values or duplicate rows (same rows the quality report already counted), write the cleaned CSV to `PDM_ARTIFACT_DIR/candidates/<uploadId>/train.csv`. This cleaned file, not the original upload, is what `fit_model` reads later — so a candidate's metrics reflect the same data the quality report described.

`uploadId` is a `uuid4` hex string generated by the endpoint, used as the candidate's directory name and returned to the caller as the handle for the next two steps.

### 3. PDM endpoints (`pdm/app/main.py`)

- **`POST /training/upload`** — multipart CSV. Runs `training_quality.assess()` on the parsed CSV. Fails → `422` with `{qualityScore, verdict: "REJECTED", reasons: [...]}`, nothing written to disk. Passes → writes the cleaned CSV under `candidates/<uploadId>/`, returns `201` with `{uploadId, qualityScore, verdict: "PASS", reasons: [], rowCount}`.
- **`POST /training/{uploadId}/fit`** — loads `candidates/<uploadId>/train.csv`, calls `training.fit_model` with `artifact_dir` overridden to `candidates/<uploadId>/` (a small param addition to `fit_model`, defaulting to the existing `_artifact_dir()` behavior so the live-artifact call sites are unaffected) so the candidate model never touches the live directory. Returns the candidate's metrics (`FittedModel.metrics`) alongside the currently-deployed model's metrics (read straight from the live `metadata.json` if present, `null` if none — e.g. right after a reset).
- **`POST /training/{uploadId}/deploy`** — copies `candidates/<uploadId>/{model.joblib,metadata.json}` over the live `PDM_ARTIFACT_DIR` files, then re-runs `model._load_artifact()` and reassigns `model._artifact` in place. Returns the newly-live metadata (including `artifactSha256`) for Node to persist.
- **`DELETE /training/{uploadId}`** — best-effort cleanup of `candidates/<uploadId>/` for a candidate the operator chose not to deploy (called by the FE's "Discard" action; not load-bearing — an orphaned candidate directory is harmless clutter, not a correctness issue).

All four are added next to the existing `/score`/`/process-window` handlers, same file, same "no auth at this layer" posture the rest of `pdm`'s internal-network-only service already has (network isolation, not app-level auth, is what currently protects it — see `docker-compose.yml`'s "no ports" comments on the `pdm` service).

### 4. Node proxy layer

New `server/controllers/trainingController.js` + `server/services/trainingService.js`, registered in `server/routes/index.js`:

```
POST   /pdm/training/upload           (uploadCsv.single('file') — reuses server/middleware/uploadFile.js as-is)
POST   /pdm/training/:uploadId/fit
POST   /pdm/training/:uploadId/deploy
DELETE /pdm/training/:uploadId
POST   /pdm/training/reset
GET    /pdm/training/runs             (thin wrapper over trainingRunModel.listRuns())
```

`requireTrustedProxy` is applied to every route here (same convention as every other non-ingestion route — it only blocks requests that bypassed Traefik/Authentik/nginx entirely, e.g. another container on the `edge` network; it does not restrict *which* logged-in user). Deliberately **no** `requireGroup(PDM_REVIEWER_GROUP)`, unlike `external-upload`'s confirm step — that's the one check that actually restricts to a role, and skipping it is what makes this "possible for anyone" (any authenticated app user, not just `pdm-reviewers`). `uploadCsv` (multer) still enforces the `.csv` extension/MIME allowlist and the existing size limit, so this isn't wide open to arbitrary file types.

`trainingService.js` forwards the multipart file to `pdm`'s `/training/upload` via `fetch` + `FormData` (same "Node calls pdm over HTTP" pattern `pdmService.js` already uses for `/score`), and forwards `fit`/`deploy`/reset calls as plain JSON `fetch` calls. On a successful `/deploy` response, `trainingService.js` calls `trainingRunModel.insertRun()` with `promoted: true` and the metadata pdm returned — Python still never writes Postgres directly (§3.4 invariant preserved, same handoff shape as `recordBootstrapRun.js`, just synchronous-over-HTTP instead of CLI-piped). `corpusContentHash` is set to `bootstrap:upload:<artifactSha256>` and `corpusRowManifest` to `{source: "upload", uploadId, rowCount}`, mirroring the existing bootstrap row's convention of describing the CSV instead of a training_corpus slice.

### 5. Client — Train Model panel

New `client/src/pages/TrainModelPage.jsx` (wired into `Sidebar.jsx`/routing the same way the existing pages are), with a linear flow:

1. File picker + "Upload" button → `POST /pdm/training/upload`. Shows the quality report: score, PASS/REJECTED, and the reasons list on reject (nothing further happens on reject).
2. On PASS: "Fit candidate model" button → `POST /pdm/training/:uploadId/fit`. Shows a comparison table: candidate vs. currently-deployed, per label class (precision/recall/support) + overall accuracy, side by side (a `null` deployed side just renders "No model currently deployed").
3. "Deploy this model" (confirm dialog — replaces whatever's live) or "Discard" (`DELETE /pdm/training/:uploadId`, returns to step 1).
4. A "Reset model" control (separate from the upload flow) calling `POST /pdm/training/reset`, for item 1's "start over" — also gated behind a confirm dialog since it's destructive.

No new client-side validation beyond file-type (`.csv`) before upload — all real validation is server-side (quality gate), matching the existing `external-upload` FE pattern.

### 6. Needs Review collapse

In `PredictionsPage.jsx`, the review-queue list component gets a `visibleCount` state (`useState(10)`). Render `sorted.slice(0, visibleCount)` instead of all of `sorted`. Below the list: if `sorted.length > visibleCount`, a "Show N more" button (`+10`, capped at `sorted.length`); if `visibleCount > 10`, a "Show less" button resetting to `10`. `visibleCount` resets to `10` whenever the filtered `sorted` array's identity changes due to a filter change (existing `filters` state already triggers a `sorted` recompute — reset in the same effect/memo boundary so switching filters doesn't leave a stale expanded count). Selection/dismiss-all behavior is unaffected — "Dismiss all shown" already operates on `sorted`, not the visible slice, so its semantics don't change from this.

## Error handling

- Bad quality → `422`, nothing written to `candidates/`, nothing touches the live artifact.
- Fit/deploy failures (corrupt CSV mid-flight, disk write failure) → `500` with a message; the live artifact is only ever touched by `/deploy`, and only after a successful `/fit`, so a failure anywhere upstream of deploy can never corrupt the currently-deployed model.
- `/training/reset` on an already-empty artifact dir is a no-op success, not an error (idempotent).
- Node's proxy layer passes pdm's status codes and bodies through unchanged (same pattern `pdmService.js` uses for `/score` failures — log and surface, no swallowing).

## Testing

- `pdm/tests/test_training_quality.py`: a good CSV passes with score ≥ 70; missing required columns hard-fails structurally; a CSV under `MIN_ROWS` hard-fails; high missing-value rate, high duplicate-row rate, high out-of-range rate, and a too-imbalanced label column each drag the score below 70 individually.
- `pdm/tests/test_training_endpoints.py` (FastAPI `TestClient`): upload→fit→deploy happy path ends with the live `metadata.json` matching the candidate's; reset clears the live artifact and a subsequent `/score` call has no `tier2*` fields; a rejected upload leaves no `candidates/` directory; deploy of a nonexistent `uploadId` returns 404.
- A couple of Node tests for `trainingService.js`/`trainingController.js` if `server/tests` has an existing pattern for controller-level tests to follow (check before writing — match convention rather than introduce a new one).
- Manual: run the FE panel end to end against a real CSV (upload a bad one, see the rejection reasons; upload `data/train.csv` itself, fit, compare, deploy, confirm Tier 2 badges reappear on a subsequent detection); manual check of the Needs Review collapse with a queue of 15+ items.
